# Аудит Quaber от 28 октября 2026

Проверена текущая рабочая копия, включая незакоммиченные изменения: frontend, backend, авторизация, хранение credentials, Kubernetes API, kubectl helper, скрипты сборки/проверки, документация и npm lockfiles. Исходники приложения не исправлялись. Запросы к реальным кластерам и изменение рабочих учётных записей не выполнялись.

Это аудит исходного проекта. Содержимое готовых архивов release/send не сверялось с исходниками; реальные RBAC, сетевые ограничения, настройки TLS и поведение конкретного Kubernetes-кластера не проверялись. Активность скомпрометированных credentials не проверялась.

P1 — исправить до использования с недоверенными пользователями или важными кластерами. P2 — существенный дефект/пробел защиты. P3 — менее срочное замечание. Приоритеты учитывают условия именно этого проекта, а не только рейтинг внешней уязвимости.

## Основной вывод

Есть критические пути выполнения кода на backend и захвата чужой учётной записи. Дополнительное подтверждение присутствует у большинства кнопок изменения ресурсов, но не гарантирует выполнение именно показанного действия: воспроизведено подтверждение удаления Pod A с фактическим обращением к Pod B. Некоторые операции доступны только через API, без клиентского подтверждения. Консоль после однократной разблокировки позволяет выполнять произвольные команды без новых подтверждений.

### 1. P1, критическая безопасность: произвольный kubeconfig позволяет выполнить код на backend

Источники: [kubectl-login-cli.ts:76](server/src/kubernetes/kubectl-login-cli.ts#L76), [store.ts:108](server/src/clusters/store.ts#L108), [kubectl-proxy.ts:75](server/src/kubernetes/kubectl-proxy.ts#L75), [router.ts:135](server/src/api/router.ts#L135).

При отсутствии password функция аутентификации возвращает входной объект без входа через helper. API продолжает принимать kubeconfigData, хотя UI импорта kubeconfig удалён. Проверка ограничена наличием current cluster/user; user.exec и другие опасные поля сохраняются. Затем исходный kubeconfig получает kubectl proxy. Пользователь панели со своей сессией и CSRF может передать конфигурацию exec-плагина через создание/обновление подключения или test-input и запустить команду с правами backend. Последствия включают доступ к DASHBOARD_MASTER_KEY и credentials других пользователей. Shell:false у spawn этого не предотвращает: программу запускает сам kubectl.

Локально подтверждено сохранение exec и обход требования password; сам exec-плагин и запросы к кластеру не запускались. Такое поведение kubeconfig описано в [официальной документации Kubernetes](https://kubernetes.io/docs/concepts/configuration/organize-cluster-access-kubeconfig/).

Исправление: убрать kubeconfigData из публичного API, отделить внутренний результат helper от пользовательского DTO; строить минимальный kubeconfig по разрешённым полям, запрещая exec/auth-provider/локальные файлы/неразрешённые proxy URL. Проверять также результат helper.

### 2. P1, критическая безопасность: любой пользователь может захватить чужую учётную запись

Источники: [auth/router.ts:19](server/src/auth/router.ts#L19), [auth/router.ts:20](server/src/auth/router.ts#L20).

GET /api/users возвращает ID всех пользователей. POST /api/users/:id/reset-password доступен любому вошедшему пользователю после смены временного пароля и возвращает новый временный пароль жертвы. После входа и обязательной смены пароля доступны её персональные подключения. Наличие CSRF не защищает от другого авторизованного пользователя. Отсутствие ролей документировано в README, но разрушает заявленную изоляцию кластеров.

Воспроизведено через реальный handleAuthRequest с отдельной SQLite в /tmp: Alice сбросил пароль Bob, получил HTTP 200 и вошёл как Bob. Рабочая база не использовалась.

Исправление: серверная проверка административной роли для управления пользователями; обычному пользователю разрешить только изменение своего пароля. Для административного сброса предусмотреть подтверждение и уведомление владельца.

### 8. P2: произвольные команды выполняются без повторного подтверждения

Источники: [PodPanel.tsx:194](client/src/components/pod/PodPanel.tsx#L194), [PodPanel.tsx:206](client/src/components/pod/PodPanel.tsx#L206), [PodPanel.tsx:290](client/src/components/pod/PodPanel.tsx#L290), [resources.ts:426](server/src/kubernetes/resources.ts#L426).

После одной проверки консоль выполняет любой /bin/sh -lc без нового подтверждения. Это реализованный режим работы, а не отсутствующая проверка одной кнопки. Он не соответствует строгому требованию подтверждать каждую потенциальную мутацию. Разбирать shell-команды эвристикой «читающая/пишущая» ненадёжно.

### 11. P2: неизвестный результат Exec отображается как завершение, позднее подключение не отменяется

Источники: [resources.ts:417](server/src/kubernetes/resources.ts#L417), [resources.ts:433](server/src/kubernetes/resources.ts#L433), [resources.ts:442](server/src/kubernetes/resources.ts#L442), [PodPanel.tsx:198](client/src/components/pod/PodPanel.tsx#L198).

Закрытие WebSocket без финального Kubernetes status вызывает resolve и возвращает status:null. UI показывает обычное «нет вывода». Если timeout сработал до подключения, socket ещё отсутствует; позднее соединение не проверяет settled и остаётся открытым. После сообщения об ошибке команда может всё же начать выполняться, а пользователь — повторить её.

Оба случая воспроизведены с mock Kubernetes Exec и исходной функцией. Исправление: отличать успех, ошибку и неизвестный результат; отменять установление соединения и закрывать поздний socket; предупреждать, что timeout не доказывает отсутствие побочных эффектов. Не делать автоматических повторов изменяющих команд.

### 12. P2: логи и Exec способны исчерпать память backend

Источники: [resources.ts:372](server/src/kubernetes/resources.ts#L372), [resources.ts:397](server/src/kubernetes/resources.ts#L397), [resources.ts:464](server/src/kubernetes/resources.ts#L464).

Вывод целиком накапливается в Buffer[], затем копируется Buffer.concat. Лимит длины команды и timeout не ограничивают объём результата. Ограничение логов числом строк также не является ограничением байт. Большой файл, длинные строки или несколько параллельных запросов могут привести к OOM.

Исправление: лимит суммарных байт, ограничение параллелизма, deadline/отмена чтения, limitBytes для Kubernetes logs и корректный признак обрезанного вывода.

### 15. P2: текущий helper не поддерживает произвольный кластер

Источники: [kubectl-login-cli.ts:85](server/src/kubernetes/kubectl-login-cli.ts#L85), [addons/kubectl:254](addons/kubectl#L254), [addons/kubectl:269](addons/kubectl#L269).

При запуске удаляются все QUABER_* из окружения, включая OIDC issuer/CA/client secret. Helper содержит issuer только для двух лабораторных адресов. Для другого URL он завершается сообщением с предложением --oidc-issuer-url, которого в parser уже нет. В текущей рабочей копии заявленный сценарий подключения произвольного кластера не работает. Это относится к находящемуся здесь helper; отдельно установленный корпоративный kubectl может иметь иное поведение.

Исправление: согласовать контракт backend/helper, явно задать поддерживаемый способ discovery/configuration и убрать лабораторные пути из общего запуска.

### 16. P2: журнал не фиксирует ресурс и исход изменения

Источники: [router.ts:118](server/src/api/router.ts#L118), [logger.ts:45](server/src/logging/logger.ts#L45).

### 17. P2: передача и обработка diagnostics могут раскрывать credentials

## Инвентаризация всех изменений Kubernetes

У всех указанных маршрутов есть общая проверка сессии, обязательной смены временного пароля и CSRF для non-GET. Cluster lookup ограничен собственными включёнными подключениями; окончательные разрешения проверяет Kubernetes RBAC. Эти меры полезны, но обход владения через захват аккаунта описан выше.

| API | Фактическое изменение | UI-подтверждение | Предупреждение и уведомление |
| --- | --- | --- | --- |
| PUT /api/configmaps/:name | Полная замена ConfigMap | Математический пример | Есть имя и cluster, нет namespace/diff/влияния на потребителей; есть сообщение сохранения |
| DELETE /api/deployments/:name | Удаление Deployment, Foreground | Кнопка в текущем UI отсутствует | API доступен без дополнительного подтверждения; опасность удаления зависимых объектов не показывается |
| PUT /api/deployments/:name | Полная замена Deployment | Пример | Есть cluster/namespace, нет diff; есть сообщение сохранения |
| PUT /api/deployments/:name/replicas | Число реплик 0–10000 | Пример | Старое/новое число и cluster/namespace; последствия нуля отдельно не обозначены; есть сообщение |
| POST /api/deployments/:name/restart | Изменение template annotation, rollout | Пример | Указан rolling restart всех Pods, cluster/namespace; есть сообщение о запросе restart |
| PUT /api/deployments/:name/resources | Resources контейнера, rollout | Кнопка в текущем UI отсутствует | API доступен без дополнительного подтверждения; удаление посторонних resource keys не объявлено |
| DELETE /api/pods/:name | Прямое удаление Pod | Пример в матрице и панели | Названо restart, owner не проверяется, cluster/namespace в диалоге отсутствуют; отдельного success-сообщения нет; в панели воспроизведена подмена цели |
| PUT /api/pods/:name | Полная замена Pod в пределах разрешённых Kubernetes полей | Пример | Нет полной цели/diff; draft перезаписывается при polling; есть сообщение сохранения |
| POST /api/pods/:name/exec | Произвольная shell-команда | Только первоначальная разблокировка | Следующие команды без подтверждений; нет полного target и явного предупреждения о мутациях; вывод команды не всегда достоверно отражает результат |

Подтверждения существуют только в React. Сервер не выдаёт одноразовый token подтверждения, связанный с пользователем, конкретной целью и хэшем действия; не требует его в мутациях, не использует dry-run и не имеет read-only режима. Само по себе отсутствие серверного диалога не является обходом авторизации: API всё ещё требует сессию/CSRF/RBAC. Но строгий процесс дополнительного подтверждения можно обойти прямым обращением к API, а два маршрута вообще не имеют UI-сценария подтверждения.

Если подтверждение должно быть обязательным свойством приложения, нужен серверный prepare/confirm механизм с коротким сроком, одноразовым идентификатором и привязкой к неизменяемой цели/payload. UI должен показывать эту же цель и последствия. Сервер способен связать подтверждение с действием, но не доказать, что человек прочитал диалог.

Чтение списков, detail, events, metrics, logs, ResourceQuota и Cluster Health не содержит мутаций объектов Kubernetes. Изменение/удаление записи подключения меняет локальные настройки Quaber. Проверка подключения вызывает listNamespace и запускает локальный proxy; из-за недоверенного kubeconfig она всё равно опасна для backend. Вспомогательные диагностические запросы читают данные; login может изменять локальный kubeconfig. Манифесты k8s/ применяются к кластеру только при отдельном ручном запуске инструмента; автоматический apply из приложения не обнаружен.
