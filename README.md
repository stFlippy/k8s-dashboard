# Quaber — Kubernetes Control Panel

Quaber — веб-панель для работы с несколькими Kubernetes-кластерами. Интерфейс показывает Pods в матрице Deployment × Namespace и даёт доступ к логам, консоли, YAML, ConfigMaps, квотам и состоянию нод.

Для Kubernetes и авторизации браузер обращается только к backend Quaber. Пароль входа вводится в браузере и передаётся backend, который проверяет его на внешнем сервере авторизации; Kubernetes kubeconfig и токены в браузер не возвращаются.

## Возможности

- персональный список кластеров для каждого пользователя;
- персональный `kubectl login` и изолированный `kubectl proxy` с тестом до сохранения;
- фильтры Pods по статусу, Deployment, Namespace и кластеру;
- подсветка недавних рестартов и ручной rollout restart;
- пользовательские вкладки с собственными фильтрами, порядком и цветом;
- импорт/экспорт вкладок с проверкой кластеров и уникальности имён;
- текущие и previous-логи, поиск и экспорт;
- защищённая консоль Pod, YAML, метрики, события и контейнеры;
- редактирование ConfigMaps с подтверждением;
- ResourceQuota; вкладка Cluster Health отключена из-за зависимости от прав на ноды;
- светлая/тёмная темы;
- внешняя проверка логина/пароля, локальные роли и 12-часовые сессии.

## Стек и схема

- frontend: React, TypeScript, Vite, TanStack Query;
- backend: Node.js, TypeScript, `@kubernetes/client-node`;
- роли, сессии и настройки: SQLite; пароли проверяет внешний сервер;
- credentials кластеров: AES-256-GCM с ключом `DASHBOARD_MASTER_KEY`.

```text
Browser -> frontend -> backend -> kubectl proxy -> Kubernetes API
                        |              |
                        |              +-> персональная identity Kubernetes
                        +-> SQLite и зашифрованный kubeconfig
                        +-> auth_server (POST username/password -> true/false)
```

## Требования и запуск

- Node.js 22.20+ и npm 10+ для разработки и сборки; автономному пакету они не нужны;
- сетевой доступ backend к Kubernetes API;
- Kubernetes identity с нужным RBAC;
- Metrics Server для CPU/RAM.

```bash
npm run install:all
cp .env.example .env
openssl rand -hex 32
```

Запишите результат последней команды в `.env`:

```dotenv
DASHBOARD_MASTER_KEY=<случайный-ключ-не-короче-32-символов>
```

Не меняйте ключ после сохранения кластеров: без него credentials расшифровать нельзя. Создайте тестового пользователя mock-сервера (см. ниже) и запустите:

```bash
npm run dev
```

- UI: `http://localhost:5173`;
- backend: `http://localhost:3001`.

Проверки и сборка:

```bash
npm run typecheck
npm run build
```

Автономный пакет для Linux x86-64, которому на целевой машине не нужны Node.js и npm:

```bash
npm run build:standalone
```

Результат создаётся в `release/quaber.tar.xz` с отдельным файлом `.sha256`; для сборки требуется `xz`. Промежуточная распакованная версия находится в `.build/standalone/quaber/`, поэтому сборка не затрагивает действующую установку в `release/quaber/` и её данные. В пакет входят backend с собственным Node runtime, собранный frontend, проверка окружения и примеры конфигурации. По умолчанию архив не содержит `kubectl` — ни `bin/kubectl`, ни `addons/kubectl`. После распаковки скопируйте совместимый Linux x86-64 клиент с командами `login` и `proxy` в `addons/kubectl` и выполните `chmod 755 addons/kubectl`; при сборке его можно включить через `QUABER_LOGIN_KUBECTL=/path/to/kubectl`. Без него Quaber запускается, но функции подключения к кластерам недоступны. Инструкция по установке и ограничения целевой машины находятся в `STANDALONE.md` и внутри архива в `README.md`.

`npm run check` дополнительно ищет секреты и намеренно падает при наличии корневого `.env`; запускайте его до создания `.env` или в чистой копии.

## Конфигурация backend

| Переменная | Назначение | По умолчанию |
| --- | --- | --- |
| `PORT` | порт backend | `3001` |
| `DASHBOARD_MASTER_KEY` | ключ шифрования, минимум 32 символа | нет |
| `USER_DATABASE_PATH` | SQLite пользователей и настроек | `server/data/users.sqlite` |
| `CLUSTER_STORE_PATH` | зашифрованные настройки кластеров | `server/data/clusters.json` |
| `STATIC_DIR` | каталог собранного frontend; автономный пакет задаёт его автоматически | не задан |

Диагностические логи управляются верхнеуровневым `quaber.config.json`. `logging.enabled: false` отключает `INFO`, но сообщения `ERROR` остаются включёнными. Поддерживаемый уровень — `info`.

## Внешняя авторизация и первый пользователь

Адрес сервера задаётся в корневом `quaber.config.json` через `authentication.url`. Для локальной проверки установлен `http://127.0.0.1:4175/api/auth/verify`; реальный удалённый сервер должен использовать HTTPS. Quaber передаёт в `POST` JSON `{"username":"...","password":"..."}` и принимает только JSON `true` или `false` с HTTP 200. Имя должно совпадать с записью в Quaber по регистру; разные регистры не объединяются в одну локальную роль. Ошибка сети, таймаут, редирект или другой ответ блокируют вход; локального запасного пароля нет. Пароль не сохраняется в SQLite.

Тестовый сервер находится в `auth_server` и запускается вместе с `npm run dev` (или отдельно `npm run dev:auth`). Он читает `auth_server/users.json`, расположенный вне раздаваемого Vite каталога `web`. Создайте пользователя командой:

```bash
npm --prefix auth_server run add-user -- admin
```

Команда сохранит salted scrypt-хэш и один раз покажет случайный пароль. Mock слушает только `127.0.0.1:4175`; не используйте его как боевой сервис. При пустой базе первый успешно авторизованный пользователь Quaber становится администратором; остальные автоматически создаются с обычной ролью. В существующей базе роли и настройки сохраняются, а старые локальные сессии завершаются при первой миграции. Администратор может выдавать и отзывать роли после первого входа пользователя. Пароли меняются на внешнем сервере, не в Quaber. Сессия Quaber действует 12 часов.

Старый `clusters.json` формата v1 больше не назначает все кластеры первому вошедшему пользователю. Для миграции задайте явное соответствие ID кластера и имени владельца в JSON-файле, например `{"cluster-id":"username"}`, и выполните `node scripts/migrate-cluster-owners.mjs --mapping /secure/path/owners.json --store /path/to/clusters.json --db /path/to/users.sqlite` после резервного копирования и остановки сервера. Скрипт сохраняет отдельную копию v1 с правами `0600`.

# Добавление кластеров

Откройте меню пользователя → `Кластеры` → `Добавить кластер`. Введите уникальное имя, API server, логин и пароль, затем нажмите `Тест`. После успешной проверки сохраните запись. Это единственный поддерживаемый способ подключения: ручной импорт kubeconfig, bearer token и basic-auth удалены.

Backend должен разрешать DNS-имя API, доверять сертификату и иметь маршрут до адреса. `localhost` означает машину/контейнер backend, не компьютер с браузером.

## Kubectl login и proxy

Режим `Kubectl login — логин / пароль` запускает серверный файл `addons/kubectl` без shell. При добавлении указываются только имя кластера, Kubernetes API server, логин и пароль.

Quaber вызывает интерфейс `kubectl login URL --username USER --password PASS`. Для каждого входа создаются отдельные временные `HOME` и `KUBECONFIG`, поэтому kubeconfig разных пользователей не смешиваются. Успешная команда должна записать kubeconfig в этот временный каталог.

Quaber больше не принимает и не передаёт OIDC issuer, CA-сертификаты и флаги отключения TLS-проверки. Определение провайдера авторизации, сертификатов и получение token полностью выполняет используемый `kubectl login`.

Пароль передаётся helper параметром `--password`, после входа удаляется из запроса и не сохраняется Quaber. Во время выполнения он может быть виден локальным пользователям сервера, имеющим право читать аргументы чужих процессов. Helper создаёт временный kubeconfig; Quaber сверяет его API endpoint и сохраняет зашифрованной только минимальную конфигурацию с bearer-токеном и встроенным CA. Exec-плагины, локальные файлы и proxy URL в kubeconfig отвергаются. После истечения токена карточка показывает `требуется пароль`; повторно вводится только пароль. Изменение адреса API или логина требует нового входа.

При первом Kubernetes-запросе Quaber запускает отдельный `kubectl proxy` для пары «пользователь Quaber — кластер». Proxy слушает только случайный порт `127.0.0.1`, использует непредсказуемый URL-префикс и останавливается после 15 минут простоя, при выходе пользователя, удалении кластера или остановке backend. Поэтому Kubernetes видит identity из персонального kubeconfig и сохраняет её в audit log. Браузер не получает ни kubeconfig, ни локальный адрес proxy.

На backend должны быть доступны Bash, `curl`, `base64`, один из `jq`/`python3`, а `addons/kubectl` должен иметь право на выполнение:

```bash
chmod 755 addons/kubectl
```

Для проверки учётных данных без установки Quaber используйте `addons/test-quaber-auth.cmd` или Linux-аналог `addons/test-quaber-auth.sh`. Они проверяют `kubectl login` и выполняют только read-only запросы; пароль в журнал не попадает.

## Тест, редактирование и ошибки

`Тест` выполняет пробный запрос до сохранения; результат закрывается крестиком. Сохранённый кластер можно редактировать и повторно тестировать. Удаление защищено математическим подтверждением и удаляет только запись Quaber, не Kubernetes-кластер.

- `404` с HTML: указан URL сайта/Ingress вместо Kubernetes API;
- `401`: credential неверен или истёк; если ошибка возникает сразу после успешного Dex login, сравните UTC-время backend, Dex и control-plane;
- `403`: соединение работает, но RBAC запрещает действие;
- timeout/DNS/`ECONNREFUSED`: backend не видит API;
- TLS error: используемый `kubectl login` не смог проверить сертификат либо hostname; `certificate is not yet valid` обычно означает рассинхронизацию времени;
- нет метрик: Metrics API отсутствует или запрещён.

Алиас содержит до пяти символов; по умолчанию используются первые пять символов имени. Он выводится отдельной фиксированной частью Namespace-заголовка, чтобы одинаковые Namespace разных кластеров не смешивались.

# Интерфейс

## Pod list и фильтры

Строки таблицы — Deployments, колонки — Namespaces. Статусные переключатели:

- `Running` — работающие Pods;
- `Restart < 1h` — новый Pod или restart контейнера за последний час;
- `Pending`, `Error`, `Unknown`;
- `Issues` — только проблемные;
- `Hide empty` — скрыть пустые Namespaces.

Restart определяется по данным Kubernetes, а не по памяти браузера, поэтому виден другим пользователям. Когда `Running` включён, отдельный restart-фильтр неактивен. Deployment с нулём Pods остаётся в таблице с серым `0`.

Автообновление: выключено, 5/10/30 секунд, 1/5 минут или целое пользовательское число минут. Интервал сохраняется в профиле; при переключении вкладки данные обновляются. Фильтры Deployment, Namespace и кластер открываются по одному и закрываются кликом снаружи.

Ширину Deployment и высоту Namespace-заголовков можно менять. Имя Namespace в таблице показывается горизонтально, максимум в две строки; `Total` считает только видимые после фильтрации Pods. Namespace и Deployments переставляются drag-and-drop с индикатором места; отпускание вне допустимой области отменяет перенос.

## Вкладки

Вкладка сохраняет фильтры, порядок, автообновление и цвет. Цвет применяется к вкладке, панелям управления и подложке таблицы. Вкладки создаются, переименовываются, удаляются и переставляются; контекстное меню открывается ПКМ. Имена уникальны.

Экспорт создаёт один JSON со всеми вкладками, включая их цвета. Импорт проверяет формат, имя и наличие кластеров. При конфликте диалог остаётся открытым до исправления или отмены; отсутствие данных не должно ломать текущую страницу.

## Deployment

Нажатие открывает боковую панель, не отдельную страницу. При одинаковом имени сначала выбираются кластер и Namespace. Доступны реплики, Pods, события, YAML, масштабирование и restart. CPU/RAM: зелёный до 75%, жёлтый 75–90%, красный выше 90%. Прочерк снабжён причиной — например, нет Metrics API или requests/limits. Подтверждение изменений явно показывает кластер и Namespace.

Неиспользуемый в UI endpoint изменения CPU/RAM контейнера требует предварительного `POST /api/deployments/:name/resources/preview` с теми же полями. Он возвращает diff четырёх управляемых значений, `resourceVersion` и предупреждение о rollout. Следующий `PUT /api/deployments/:name/resources` должен передать `expectedResourceVersion` и `acknowledgeRollout: true`; остальные resource keys сохраняются.

## Pod

Панель содержит текущие/previous-логи, консоль, статус, YAML, метрики, события и контейнеры. Логи автоматически прокручиваются, поддерживают поиск и экспорт с именем `<pod>-<container>-ДД.ММ.ГГГГ-ЧЧ.ММ.log`. Previous-лог отмечен как «Лог предыдущего запуска».

Консоль изначально заблокирована. Разблокировка действует до закрытия вкладки или пяти минут простоя; замок в заголовке позволяет заблокировать команды. Enter принимает ответ проверки и выполняет команды, клик по области фокусирует ввод.

## YAML и ConfigMaps

Редакторы имеют фиксированную область, номера строк и поиск. Enter переходит к следующему совпадению, стрелки — вперёд/назад; при нуле совпадений позиция не меняется. Счётчик показывает текущий и общий результат. Сохранение валидирует документ и требует подтверждения; модалки закрываются крестиком.

В списке ConfigMaps одновременно выбирается один кластер и один Namespace; при смене кластера показываются его Namespace, чтобы не смешивать объекты разных источников.

## ResourceQuota

ResourceQuota показывает только реально созданные Kubernetes-объекты `ResourceQuota`: hard и used. Пусто означает отсутствие квот, а не нулевую фактическую нагрузку; ошибки RBAC и сети показываются отдельно.

В метриках Pod при отсутствии Metrics Server может использоваться fallback через kubelet `/stats/summary`, а CPU throttling рассчитывается по дельте cAdvisor-счётчиков между обновлениями. Для такого fallback требуется `get` на `nodes/proxy`. **Это не минимальное read-only право:** тот же доступ к proxy может открывать и другие операции kubelet, включая выполнение команд. Не выдавайте `nodes/proxy` только ради наблюдения без оценки рисков; предпочтительнее Metrics API. Права `nodes/stats` и `nodes/metrics` не являются прямой заменой `nodes/proxy` для текущего URL через API server.

## Темы и пасхалка

Тема переключается ползунком в `Личное` и сохраняется за пользователем. Если в Deployment-фильтр ввести `йцукенqwerty`, интерфейс сменяется анимированным ASCII-котом; очистка возвращает страницу.

# Безопасность

- пароли входа не сохраняются Quaber; тестовый `auth_server` хранит salted scrypt-хэши;
- cluster credentials: AES-256-GCM;
- session cookie: `HttpOnly`, `SameSite=Strict`, а под HTTPS — `Secure`;
- SQL-запросы параметризованы;
- ввод валидируется по типу, длине и формату на frontend/backend;
- YAML, логи и ошибки выводятся как текст, не HTML;
- секретные API-ответы используют `Cache-Control: no-store`;
- неизвестные маршруты показывают страницу 404;
- необратимые действия защищены математическим подтверждением.
- мутации Kubernetes записываются в SQLite с пользователем, целью, результатом HTTP и ID операции без паролей и полных манифестов; срок хранения задаётся `mutationAudit.retentionDays` в `quaber.config.json` (по умолчанию 30 дней).

Вкладка `Сервер` показывает CPU/RAM/диск хоста, размер SQLite и последние действия текущего пользователя. Уровень обычного журнала задаётся `logging.level`: `debug` включает чтения и автообновления, `info` оставляет значимые действия, `error` — только ошибки. Отдельный SQLite-журнал мутаций от этого флага не зависит. Quaber умеет exec и изменять workloads. Защищайте его TLS, сетью и Kubernetes RBAC, используйте отдельные identities и не выдавайте `cluster-admin` без необходимости.

# Production и резервные копии

```bash
npm run build
```

`npm start` запускает обычный backend для размещения за static server/reverse proxy: публикуйте `client/dist` и проксируйте `/api` на backend. Автономный пакет сам раздаёт вложенный frontend. Передавайте `X-Forwarded-Proto: https` для cookie `Secure`.

Храните на постоянных volumes SQLite и runtime data. Резервируйте SQLite, legacy store при наличии и `DASHBOARD_MASTER_KEY` вместе, но в разных защищённых системах. Без master key credentials не восстановить. Старые bootstrap-файлы больше не используются и могут содержать открытые пароли; удаляйте их после проверки миграции.

# Диагностика

Метрики:

```bash
kubectl get apiservice v1beta1.metrics.k8s.io
kubectl top nodes
kubectl top pods -A
```

RBAC:

```bash
kubectl auth can-i list pods -A --as=system:serviceaccount:quaber-system:quaber
kubectl auth can-i get pods/log -A --as=system:serviceaccount:quaber-system:quaber
kubectl auth can-i create pods/exec -A --as=system:serviceaccount:quaber-system:quaber
```

Previous-лог существует лишь для предыдущего экземпляра контейнера в том же Pod. После удаления Pod или нового rollout его отсутствие нормально.

При `401` обновите credential и повторите `Тест`. При TLS error проверьте системное доверие, настройки используемого `kubectl login` и SAN сертификата. Ошибка одного кластера должна отображаться локально и не блокировать остальные.
