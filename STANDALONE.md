# Quaber standalone — Linux x86-64

Архив `quaber.tar.xz` предназначен для сервера без Node.js и npm: runtime встроен в исполняемый файл `quaber`. Нужен Linux x86-64 с glibc и стандартными системными библиотеками (в том числе `libstdc++`); Alpine/musl без совместимого окружения не поддерживается. Для HTTPS должны быть доступны доверенные CA-сертификаты, а часы сервера синхронизированы.

В архиве находятся веб-интерфейс и backend, но по умолчанию **нет исполняемого `kubectl`**: ни `bin/kubectl`, ни `addons/kubectl`. Quaber может запуститься без него, однако вход в кластеры и функции, требующие подключения к Kubernetes, будут недоступны. Для работы с кластерами добавьте в `addons/kubectl` свой совместимый Linux x86-64 исполняемый файл с командами `login` и `proxy`.

## Подготовка пакета

На машине сборки нужны Node.js 22.20+, npm 10+ и зависимости проекта. Сборка:

```sh
npm run build:standalone
```

Результат — `release/quaber.tar.xz`; для сборки и распаковки нужна поддержка `xz`. Рядом создаётся файл `quaber.tar.xz.sha256`. Установленный на машине сборки `kubectl` не включается в архив автоматически.

Если нужно включить свой совместимый `kubectl` в архив уже при сборке, укажите его путь:

```sh
QUABER_LOGIN_KUBECTL=/absolute/path/to/corporate-kubectl npm run build:standalone
```

`QUABER_LOGIN_KUBECTL` указывает на исполняемый файл **на машине сборки**; в этом случае он будет помещён в `addons/kubectl`. По умолчанию удобнее добавить файл после распаковки. Не переносите в архив пароль, kubeconfig или частные CA-файлы без отдельного решения об их защищённом хранении.

Корпоративный клиент должен поддерживать `login URL --username USER --password PASS`, записывать kubeconfig по переменной `KUBECONFIG` и поддерживать команду `proxy` с обычными флагами `kubectl`. Quaber запускает его с отдельными временными `HOME` и `KUBECONFIG` для каждого входа. Поскольку пароль передаётся аргументом процесса, ограничьте локальный доступ к серверу: во время выполнения он может быть виден пользователям, имеющим право читать аргументы чужих процессов. Перед развёртыванием проверьте совместимость клиента на тестовом кластере.

## Первый запуск на сервере

```sh
tar -xJf quaber.tar.xz
cd quaber
umask 077
cp .env.example .env
chmod 700 data
chmod 600 .env quaber.config.json
```

Для работы с кластерами скопируйте свой Linux x86-64 клиент с командами `login` и `proxy` в распакованный пакет и разрешите его выполнение:

```sh
cp /absolute/path/to/your-kubectl addons/kubectl
chmod 755 addons/kubectl
```

Если клиент ещё не готов, настройку и запуск Quaber можно продолжить без него; Kubernetes-функции станут доступны только после его добавления.

В `.env` заполните `DASHBOARD_MASTER_KEY` постоянным случайным значением длиной не менее 32 символов; лучше использовать 64 случайных шестнадцатеричных символа, полученных на доверенной машине. В `quaber.config.json` выберите `authentication.mode`: `external` (по умолчанию) или `local`. Для `external` укажите `authentication.url` реального сервера авторизации. Он должен принимать `POST` с JSON `{"username":"...","password":"..."}` и отвечать JSON `true` или `false`. Для удалённого сервера обязателен HTTPS; HTTP допускается только для mock-сервера на loopback. Режим `local` использует salted scrypt-хэши в SQLite и не обращается к серверу авторизации. После заполнения файлов выполните:

```sh
./check-runtime.sh
```

Проверка охватывает локальные условия запуска; успешный результат не означает успешную авторизацию в кластере.

Запустите сервер от отдельного непривилегированного пользователя, которому доступны каталог приложения и запись в `data`:

```sh
./quaber
```

Адрес для локальной проверки — `http://127.0.0.1:3001`. Backend слушает порт на всех интерфейсах, поэтому не открывайте его напрямую в Интернет: ограничьте доступ межсетевым экраном и используйте HTTPS-реверс-прокси для внешних пользователей. В режиме `external` первый успешно авторизованный пользователь пустой SQLite-базы становится администратором; остальные создаются после первого успешного входа с обычной ролью. В режиме `local` первый администратор создаётся через одноразовый bootstrap-файл (см. ниже). При переключении режима старые сессии завершаются, но роли и настройки сохраняются.

`data` содержит SQLite-базу и зашифрованные kubeconfig. Делайте резервные копии `data`, `.env` и `quaber.config.json` с ограниченным доступом. При обновлении остановите Quaber, сохраните эти файлы, замените остальные и запустите снова. **Не меняйте `DASHBOARD_MASTER_KEY` без миграции**: старые сохранённые реквизиты перестанут расшифровываться. Не перезаписывайте настроенный `authentication.url` тестовым адресом из нового архива. Изменения `.env` и `quaber.config.json` требуют перезапуска backend.

Для перехода с внешней авторизации на локальную остановите Quaber и сделайте резервную копию `data/users.sqlite`. Если у администратора ещё сохранился старый локальный пароль, достаточно выставить `authentication.mode` в `local` и перезапустить сервер. Если у администратора нет локального пароля, создайте `data/bootstrap-user.json` с JSON `{"username":"ТОЧНОЕ_ИМЯ_АДМИНИСТРАТОРА","password":"ВРЕМЕННЫЙ_ПАРОЛЬ_НЕ_КОРОЧЕ_12_СИМВОЛОВ"}` и правами `0600`. При старте пароль существующего администратора заменится salted scrypt-хэшем, файл будет удалён, а после входа потребуется смена временного пароля. В пустой базе этот файл создаст первого администратора. Для остальных пользователей, созданных ранее только через внешний сервер, администратор может сгенерировать временные пароли через раздел `Пользователи`. Не удаляйте `data/users.sqlite`, `data/clusters.json` и `.env`: в них остаются роли, настройки, кластеры и ключ для расшифровки. Не храните bootstrap-файл в архиве и не оставляйте его после запуска.
