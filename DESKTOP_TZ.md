# Техническое задание: десктопная версия Quaber

Статус: основные требования собраны. Реализация запланирована отдельным этапом.

## 1. Цель

Создать самостоятельное десктопное приложение Quaber на Python и PyQt. Интерфейс должен строиться средствами Qt, без браузера и встроенного веб-движка. Работа с Kubernetes, хранение данных и остальные функции нынешнего Node backend переносятся на Python. Для запуска приложения не должны требоваться Node.js, npm, браузер или отдельный сервер Quaber.

Первая целевая платформа — Windows 10 версии 1809 и более новые версии Windows, x86-64. Второй этап — Astra Linux, x86-64. Точная версия Astra Linux пока неизвестна; её совместимость и требования к сборке определяются перед вторым этапом.

## 2. Общие принципы переноса

- Перенести все **используемые сейчас** функции Quaber. За исходный образец поведения принять текущую работающую версию проекта, а документацию использовать для уточнения сценариев.
- Максимально близко воспроизвести расположение элементов, цвета, темы, матрицу и поведение интерфейса. Если конкретное поведение нельзя разумно повторить средствами Qt, предложить точечное изменение на согласование до реализации этого элемента.
- Сохранить текущий язык интерфейса и существующее сочетание русских и английских названий.
- Поддержать нормальную работу на ноутбуке с экраном 15,6 дюйма и на мониторе от 21 дюйма. Основной ориентир — 1920×1080; учитывать масштабирование ОС, а для широких таблиц обеспечить прокрутку.
- Приложение работает локально на компьютере пользователя. Общая база данных и сервер синхронизации не нужны.
- Новое приложение начинает с пустыми данными. Импорт существующих кластеров, пользователей, вкладок и настроек из веб-версии не требуется.

## 3. Функции интерфейса

### 3.1. Кластеры и настройки

- Добавление, проверка, редактирование, удаление и повторный вход в кластеры, как в текущем Quaber.
- Персональные для данной копии приложения вкладки, фильтры, порядок элементов, темы и параметры автообновления.
- Импорт и экспорт вкладок в существующем пользовательском формате, с проверками конфликтов и доступности кластеров.
- Понятные сообщения об ошибках подключения, авторизации, TLS, DNS и Kubernetes RBAC.

### 3.2. Матрица Pods

- Матрица Deployment × Namespace для нескольких кластеров.
- Текущие фильтры по состоянию, Deployment, Namespace и кластеру; подсветка недавних рестартов и пустых Deployment.
- Автообновление с нынешними интервалами, ручное обновление и сохранение настроек вкладок.
- Перестановка вкладок, Deployment и Namespace перетаскиванием; изменение ширины и высоты элементов, где это есть сейчас.
- Переход к панелям Deployment и Pod из матрицы.

### 3.3. Ресурсы Kubernetes

- Панель Deployment: сведения, реплики, Pods, события, YAML, метрики, масштабирование, restart и остальные доступные сейчас действия.
- Панель Pod: текущие и предыдущие логи, поиск и экспорт, консоль с действующей защитой подтверждения, статус, YAML, метрики, события и контейнеры.
- Просмотр и редактирование ConfigMaps, просмотр ResourceQuota.
- Сохранить действующие подтверждения опасных операций, предварительный просмотр изменений ресурсов и защиту от изменения объекта между просмотром и сохранением.
- Сохранить текущие правила обработки ошибок и отображения недоступных метрик.
- Функции, уже отключённые в текущем интерфейсе, не включаются автоматически в объём переноса.

## 4. Подключение к Kubernetes

- Использовать имеющийся корпоративный `kubectl` для Windows и Linux. Его интерфейс команд, включая `login` и `proxy`, должен воспроизводиться по текущей реализации Quaber. Сценарии работы и результаты команд не должны меняться для пользователя.
- Исполняемый файл `kubectl` **не входит** в поставку приложения. Приложение ищет его в каталоге `addons` рядом с собой и в `PATH`; при отсутствии сообщает, что нужно сделать для подключения.
- Сохранять изоляцию временных `HOME` и `KUBECONFIG` при входе, проверку результата входа, персональное использование kubeconfig и завершение запущенных `proxy`, как в текущем Quaber.
- Не сохранять пароль Kubernetes. После истечения авторизации запрашивать его повторно.
- Сохранять полученный kubeconfig между запусками приложения в защищённом локальном виде, чтобы действующее подключение восстанавливалось без повторного ввода пароля.
- Сетевые запросы и запуск внешних процессов не должны блокировать интерфейс Qt.

## 5. Локальные данные и безопасность

- Хранить список кластеров, настройки, журнал действий и защищённый kubeconfig в папке `UserData` рядом с приложением.
- Вся portable-папка, включая `UserData`, должна переноситься на другой компьютер с сохранением действующих подключений, пока их Kubernetes-авторизация действительна.
- Поэтому материал, необходимый для расшифровки kubeconfig, должен переноситься вместе с `UserData`. Полный доступ к portable-папке фактически даёт доступ к сохранённым подключениям; ответственность за защиту и распространение папки несёт её владелец/распространитель. Шифрование не следует описывать как защиту от лица, получившего всю папку.
- Отдельного входа в Quaber нет: приложение доступно после входа пользователя в ОС. Проверка логина через внешний сервер авторизации, локальные роли и экран управления пользователями Quaber в десктопной версии не нужны.
- Сохранить в применимой форме валидацию входных данных, аудит изменений Kubernetes и исключение паролей и секретов из диагностических логов.
- При отсутствии прав записи в `UserData` показывать понятную ошибку; не терять молча настройки и данные подключения.

## 6. Поставка и обновление

- Первый выпуск для Windows — portable-папка, запускаемая без установки, прав администратора и отдельно установленного Python.
- Обновление вручную: заменой файлов приложения с сохранением папки `UserData`. Автоматическая проверка и установка обновлений не требуются.
- `kubectl` распространитель добавляет в `addons` либо настраивает через `PATH`.
- После готовности Windows-версии собрать и проверить вариант для Astra Linux. Точную версию Astra Linux и способ упаковки для неё определить перед этим этапом.

## 7. Этапы реализации

1. Зафиксировать поведение текущей версии на эталонных сценариях и подготовить структуру Python-приложения, локальное хранилище и работу с корпоративным `kubectl`.
2. Реализовать подключение кластера и модели данных, затем матрицу Pods и её настройки.
3. Перенести панели Pod/Deployment, ConfigMaps, квоты, логи, консоль, YAML и все доступные действия.
4. Довести визуальное соответствие, темы, масштабирование, диагностику и portable-сборку Windows.
5. Провести приёмочную проверку на этом ПК с реальным кластером.
6. После Windows-выпуска уточнить версию Astra Linux, подготовить сборку и проверить её на целевой системе.

Этапы разработки не сокращают объём первого Windows-выпуска: он считается готовым после переноса всех используемых функций.

## 8. Критерии приёмки Windows-версии

- Приложение запускается на Windows 10 1809 x86-64 из распакованной portable-папки без Node.js, браузера и отдельно установленного Python.
- Подключение к тестовому кластеру через имеющийся `kubectl` работает при размещении файла в `addons` и при нахождении через `PATH`.
- Работают сценарии текущего Quaber: просмотр нескольких кластеров, матрица, фильтры, вкладки, автообновление, панели Pod/Deployment, логи, консоль, YAML, ConfigMaps, квоты и доступные изменения ресурсов.
- Проверены операции, меняющие ресурсы, на согласованном тестовом кластере: масштабирование, restart, изменение YAML/ConfigMaps и удаление Pod.
- Настройки и подключение сохраняются после перезапуска. Копирование portable-папки на другой компьютер переносит данные и действующий kubeconfig. После истечения авторизации запрашивается пароль.
- Интерфейс корректно масштабируется и остаётся пригодным для работы на 15,6-дюймовом ноутбуке и мониторе от 21 дюйма.
- Замена файлов приложения при ручном обновлении не удаляет `UserData`.

## 9. Открытые вопросы перед этапом Astra Linux

- Точная версия и конфигурация Astra Linux.
- Проверка совместимости Qt, упаковки Python и корпоративного `kubectl` на целевой системе.
- Формат поставки для Astra Linux и проверка переносимости `UserData` между Windows и Linux.
